# Mika 降费第二轮：缓存优先的上下文实施方案

编写日期：2026-11-12。执行者：Codex。前情见[酒店任务复盘](2026-11-12_酒店任务上下文与成本优化复盘.md)。

**一句话**：第一轮减少了输入 token，但多次回头改写已发过的历史，把便宜的命中缓存变成了贵 50 倍的未命中，结果更贵。本轮改为**已发出的请求前缀一律不动，只在新内容第一次发出时压缩**。

## 1. 为什么要改方向

### 1.1 钱花在哪

价格按每百万 token 计：命中输入 0.04 元，未命中输入 2 元，输出 8 元。原版酒店任务一次成功花 1.5167 元，构成如下：

| 部分 | token | 费用（元） | 占比 |
| --- | ---: | ---: | ---: |
| 命中缓存的输入 | 9,411,840 | 0.376 | 25% |
| 未命中的输入 | 529,218 | 1.058 | 70% |
| 输出 | 10,229 | 0.082 | 5% |

未命中平均每步约 12K token，基本就是每一步新读到的那一屏。第一轮精简旧历史，只能降低命中那 25%；把旧历史全删光、也不付出任何代价，最多省 0.376 元。

### 1.2 回头改写旧消息为什么几乎必亏

服务商按前缀缓存。改写某一条已发过的消息后，从它开始到请求末尾的所有 token 都要重算未命中。设这部分有 L 个 token，改写后每次请求少发 D 个 token，则回本需要的后续请求数为：

\[ N^* = \frac{L \times (2 - 0.04)}{D \times 0.04} \approx 49 \cdot \frac{L}{D} \]

L 至少包含整理后的旧屏幕和保留原样的最近 5 轮，通常 L ≥ D，所以回本要几十到上百步，而酒店任务总共只有 35 到 45 步。14:22 那次运行在第 41 步整理，只剩 3 次请求，当步多出 184,204 个未命中输入（约 0.37 元），注定收不回来。

### 1.3 已定位的缓存失效来源

| 来源 | 位置 | 何时引入 | 影响 |
| --- | --- | --- | --- |
| 旧屏幕改成表格 | `ReliableScreens.project`，由 `ContextCompressor` 在 `reliable = true` 时每次请求调用 | 第一轮 | 第 11、21、41… 步改写 |
| 旧大树归档 | `ArchivedScreens.project`，在 `ModelCaller.kt` 第 185 行每次请求调用 | 第一轮 | 与上一行同时改写 |
| 旧的重复图片换成占位 | `ReliableScreens.sameImages`，在 `ContextCompressor.images()` 中调用 | 第一轮 | 与上一行同时改写 |
| 第 7 步才提供 `history_read` | `AgentLoop.refreshOffer` 中的 `step >= 7` 条件 | `d86fba93` | 工具定义排在请求最前，一变整份缓存失效；真机第 7 步多出 64,571 个未命中 |
| 展开新工具组时改系统提示词 | `AgentLoop.refreshOffer` | 原版就有 | 同样会让整份缓存失效；本轮只记录，不改 |

### 1.4 回放证据

用现有 34 步酒店回放（`HotelContextReplayTest` 的合成页面、真实请求适配器、`HotelReplayMeter` 计价，工具表固定），同一条轨迹比较几种做法，另外把轨迹延长到 45 步，以覆盖第 41 步的整理点。测试代码是临时写的，跑完已删除。

| 做法 | 34 步费用 | 45 步费用 |
| --- | ---: | ---: |
| A. 历史只追加、从不改写（合成轨迹的对照） | 0.6626 | 0.9362 |
| B. 当前版：回头整理旧屏幕 | 0.7391（比 A 贵 11.6%） | 1.0544（比 A 贵 12.6%） |
| C. 只追加，新屏幕第一次发出时就写成表格 | 0.5941（比 A 省 10.3%） | 0.8347（比 A 省 10.8%） |

B 的输入比 A 少 31% 到 38%，费用反而更高，和真机现象一致。这些数字基于合成页面和项目自己的 token 估算，前提是相邻请求的公共前缀都能命中缓存，只能说明方向，不代表账单。

## 2. 设计原则

1. **已发出的请求前缀不变。** 包括工具定义、系统提示词、开局上下文和每一条历史消息。唯一例外是上下文逼近窗口、由原有 `ContextCompressor` 触发的压缩，以及服务商明确的图片上限。
2. **压缩发生在内容第一次发出时**，以后不再改动。
3. **评价指标是未命中输入和整次费用**，不是总输入 token。
4. **一次只改一个因素。** 长任务增量摘要（`semanticSummaries`）继续关闭。

## 3. 范围

**本轮要做**：T1 到 T4 必做；T5 放在开关后面，供配对实测。

**本轮不做**：

- 不改展开工具组的机制。T4 的统计会告诉我们它在真机上触发多少次，下一轮再定。
- 不缩小当前屏幕的界面树，不改差异屏幕，也不改导航路径。这些会改变模型看到的内容，单独立项。
- 不删任务事实、来源版本、恢复检查、`CompletionPlan` 这些可靠性功能。它们不改写历史，与本问题无关。
- 不删 `ReliableScreens` 和 `ArchivedScreens` 这两个类。T1 只改它们的调用时机。

## 4. 任务

### T1（P0）正常流程中不再回头改写历史

**为什么**：这是第一轮多花钱的主要来源，见 1.2 和 1.4。

**改哪里**：

- `core/.../agent/ContextCompressor.kt`：`current()` 和 `compress()` 在**没有触发压缩**时，不再对历史调用 `screens.project(...)`，`images()` 也不再调用 `sameImages`。只有 `compact()` 真正改写时（`Compressed.rewritten == true`），才可以先用 `ReliableScreens` 把输入整理成表格，再走原来的阶梯。既然这次已经要改写，顺便整理能让压缩更有效。`overflow()` 同理。
- `core/.../agent/ModelCaller.kt` 第 185 行：`archiveViews.project(original, memory)` 不能每次请求都调用。改为只在压缩器这次确实要改写时才归档；或者在 T1 中先停用，交给后续评估。选哪种由执行者按改动量决定，在提交说明里写明。
- `ModelCaller.kt` 第 197 行依赖 `consumeProjectionChange()` 来清理锚点，T1 改完后要确认这里仍然正确。

**验收**：

- 窗口 1,000,000、任务不超过 100 步、未触发压缩时，相邻两次请求的消息列表满足「前一次是后一次的前缀」（运行时状态接在本步最后一条消息末尾，这是现有的只追加行为，不算改写）。
- 压缩阈值附近的现有测试（`ContextCompressorTest`、`UsageMeterTest`）继续通过：真正触发压缩时，行为和改写次数的上限不变。
- `HotelContextReplayTest.productProjectionRetainsEveryCandidateWithoutManualPins` 断言的改写点 `[10, 20, 40, 80]` 改为空列表；「三家酒店候选和路线都还在」这一断言保留。

**预期收益**：回放中比当时的整理策略省约 10% 到 11%，接近同轨只追加策略的估算费用。真机预计能把第 11、21、41 步这类改写带来的额外未命中去掉；14:22 第 41 步一次就约 0.37 元。

### T2（P0）一个任务内工具列表保持不变

**为什么**：工具定义排在请求最前面，第 7 步加入 `history_read` 会让整份缓存失效。

**改哪里**：`AgentLoop.refreshOffer` 中的这段条件：

```kotlin
if (tools.ctx.taskMemory == null || step >= 7 || spec.name != HISTORY_READ) spec
else if (tools.ctx.config.runRecords != null && rawPrior.any { it.runId != null }) HistoryRead.def.spec() else null
```

改为：只要 `step >= 7` 时会提供 `history_read`，就从第 1 步起提供同一份定义（同样的 schema 和描述），去掉按步数的切换。如果前几步调用它时确实没有可读内容，由工具执行端返回明确的空结果或说明，不要把工具藏起来。先确认 `HistoryRead` 在开局没有可读内容时会返回什么，必要时补一条测试。

**验收**：

- 新增测试：任务进行 10 步，期间没有展开新的工具组时，每次请求的工具列表和系统提示词逐字相同。
- 第 1 步调用 `history_read` 不会抛异常，返回可以理解的结果。

**预期收益**：每个任务少一次整份缓存失效，按真机 14:11 第 7 步估算约 0.13 元。前缀越长，失效越贵，所以收益随失效发生的时间点变化。

### T3（P0）回归护栏

**为什么**：让「把命中变成未命中」的改动在测试里直接失败，而不是等真机账单才发现。

**改哪里**：`core/src/test/.../agent/HotelContextReplayTest.kt` 和 `HotelReplayMeter.kt`。

- `replayOrderPageAndPriceOnTheSame34Requests`：`assertEquals(listOf(11, 21), wire.rewrites)` 改为断言空列表，`changes["tables"]` 和 `changes["archive"]` 同样为空。费用断言改为不高于只追加的基线：同一份合成数据实测为 0.66255136 元，可以留 1% 余量。选店和订单页的断言保持不变。
- 新增 45 步变体，覆盖第 40 轮整理点：断言 `rewrites` 为空，费用不高于只追加的基线 0.93615964 元（同样留 1% 余量）。
- `HotelReplayMeter` 已经能区分工具区和消息区的首个变化块。如果能低成本区分「工具或系统提示词变了」和「历史消息变了」，请在 `toString()` 里分开显示。

**验收**：在 T1 和 T2 之前的代码上，新断言应该失败；在 T1 和 T2 之后通过。请在提交说明里写明这一点已经确认过。

### T4（P0）在真机记录中看得见前缀被打断

**为什么**：以后的真机复盘可以直接回答「哪一步、因为什么、重算了多少 token」，不用再靠两份导出人工对齐。

**做法**：先查清 `RunTrace` 和 `RunEvent` 现在已有哪些前缀变化信息，复盘文档说 RunTrace 能定位首个变动块。在此基础上，每次主循环请求发出时，如果相对上一次请求不是只追加，就记一条事件，包含：步数、原因（`tools` / `system_prompt` / `history` / `compaction`）、变化点之后的估算 token 数。只记元数据，不记正文，不记设备或订单信息。没有变化不记。

**验收**：单元测试覆盖四种原因各一例，以及只追加时不记事件。导出字段写进 `RunStore` 的导出说明。

**顺带测量（不改代码）**：`ModelCaller` 每次请求末尾都会附上任务事实（`memory.projection()`）。它不在历史里，所以每一步都是未命中。请在 T4 的事件或日志里同时记下它的估算 token 数，便于判断是否值得处理。

### T5（P1，放在开关后面）新屏幕第一次发出时就写成表格

**为什么**：未命中主要来自每步新读到的屏幕。在第一次发出时就缩小它，同时减少未命中和命中，而且不破坏缓存。回放中比只追加再省约 10%。

**做法**：

- 新增开关，例如 `SpeedFlags.tablesAtBirth`，默认关闭，在开发者选项里提供，命名和说明与现有开关保持一致。
- 开关打开时，在工具结果**加入历史之前**，对带 `elements` 的屏幕结果使用与 `ReliableScreens.pack` 完全相同的表格写法，把可复用的逻辑提出来，不要复制一份。表格不丢信息，用 `ReliableScreens.elements()` 可以还原。
- 证据账本、观察编号（`obsIds`）、差异基准（`base` / `snapshotId`）、`ArchivedScreens` 需要的字段都必须与原来一致。原始结果仍按现在的方式保存在证据和运行记录中。
- 只改 `elements` 的写法，不去掉当前屏幕的 `tree`。
- 确认系统提示词或工具说明里描述元素列表的地方，对 `elementTables` 也说得通。模型按 `ref` 点击的能力不能退化。

**验收**：

- 回放中，开关打开时 34 步费用不高于 0.5941 × 1.02 元，45 步不高于 0.8347 × 1.02 元，并且选店结果正确。
- 「三家候选与三条步行路线都可读」的断言在开关打开时也通过。
- 新增测试：表格写法经 `ReliableScreens.elements()` 还原后，与原始 `elements` 完全相同。

**预期收益**：回放中比只追加策略再省约 10%。真机收益取决于元素列表占每步新增 token 的比例，T4 上线后用真机数据确认。
