# 长任务上下文改造与验收

发布目标：fork 的 `codex/reliable-task-context` 分支及该分支的可安装测试包。A 是关闭新策略时当前 Mika 的行为。冻结起始条件、模型、日期、候选与路线；真实订单仅用于用户最终验收，不用于开发回放。

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| 1 计量 | 对照运行期总调用、HTTP 尝试、输入/缓存/输出、费用和结果；区分缺报与零。 | 新旧导出均可比较，不双算缓存或旁路；失败任务计入尝试次数和总支出；每个成功任务成本只除以已核实成功数。 |
| 2 确定性视图 | 旧工具结果、窗口历史和截图与完整证据分开；通过实际读取校验来源，保留用户约束、证据字段、依赖基准、工具配对及模型私有信息。 | 无人工标注的跨 App 酒店、30/100 步及短任务对照；不存在、冲突、过期或超预算不得导致错误选择。 |
| 3 任务记忆与交接 | 有来源/版本的事实与任务状态，处理纠正、进度与终止条件、证据读取和持久化断点。 | 新指令先于下一决策生效，未知外部动作先查结果；中断、重启、并发/写失败不丢已提交数据、不重发未知动作。 |
| 4 可选增量摘要 | 分块、增量、去重、事务性提交；独立无工具的轻量模型优先，计入运行预算，失败时保留确定性视图。 | 模型异常、版本冲突、取消、模型切换、合并均有对照；未经非劣验证不默认开启语义压缩。 |
| 5 发布 | 核查成本、前缀与可靠性，生成便于 A/B 的构建与复测说明，仅推送 fork。 | 相关 JVM、协议前缀、Android 构建、项目检查；校验远端分支、提交和 APK。实机服务商用量与订单由用户最后独立验收。 |

实际成功口径：按好评排序取前三家非民宿，三家到同一终点均用步行路线，预订对象与最近者一致，回复含正确地点、价格和时间。缺任何候选的路线不能宣称已确定最近者。测试中的结构校验不等同真实模型成功率。

## Fork 验收包的实际行为

同一个 Mika Dev 包可做三组对照。在「开发者选项 → 实验」中，A 关闭「精简任务历史」和「长任务增量摘要」；B 只开前者（此 fork 的首次默认值）；C 两项都开。用户手动关闭后不会在下次启动时重开。安装 `.dev` 包可与正式版并存；它不会继承正式版的模型和权限设置。保持模型、其他速度开关、应用账号和起始页面一致。

| ID / 优先级 | 问题、证据及原行为 | 本分支处理与验收后行为 | 预期收益 / 改动风险 | 状态 |
| --- | --- | --- | --- | --- |
| C1 / P0 | 逐步用量漏掉旁路，输入又包含缓存。只比输入总量可能得出错误费用结论。 | 导出按模型/用途分组，`eval/usage_compare.py` 同时列出命中、未命中、输出、请求和每个核实成功任务的用量；费用缺单价或用量时留空。 | 能区分少走步骤、缩短单步和换模型；旧日志不能倒推出价格或页面内容。 | 已实现 |
| C2 / P1 | 模拟的固定五轮窗口丢失早期酒店/路线页；相同字段名、树和相同截图反复发送。 | 旧元素按列保存；大树有可读的当前任务原文指针才外置。已发指针不淘汰，存满就保留原文；用户照片、最新轮次、不同像素和差异依赖另外保护。 | 长轨迹减少重复输入；窗口移动也可能增加未缓存输入，模型对表格的理解仍要实测。 | 已实现，默认 B |
| C3 / P0 | 指标到点不一定等于完成多项验收；改口、同名或被替换的观察可能把旧值带入新决策。 | 当前运行可按观察 ID、关键词、事实键和版本读取。重要摘录要在来源中逐字存在；活跃来源在内存固定，版本更新保留旧记录。改口使旧事实失效，重新确认需要改口后的来源。B 单靠计数不会提前收尾。 | 减少错选和重新采集；逐字匹配不能证明模型把价格、对象或路线语义关联正确。 | 已实现 |
| C4 / P0 | 操作可能已发出，但进程没来得及确认或交出结果，盲目继续会重复提交。 | 对识别为不可逆的屏幕动作，先写私有断点；中断后保留操作不明标记、来源轮次和可核对的引文。继续时允许检查，不自动重发已识别的危险动作。 | 降低重复下单风险；未知状态会保守停止。既有不可逆识别未命中的自绘控件不具备这个保证。 | 已实现 |
| C5 / P2 | 每次重写全历史的摘要可能比节省的输入更贵，也可能引入没有来源的事实。 | C 每次只提交新的一批旧观察，模型只选 ID，无执行工具；两块同级合并至三级。任务预算和按模型计量沿用主链路；调用失败、取消、已纠正、缺源或版本冲突不提交。 | 有机会进一步缩短大屏幕；可能增加请求、延迟或回读。默认关闭，待 B 合格后单测 C。 | 已实现，单独实验 |

**实机验收**：先用 B 对比已核实的 A。在固定任务上核对前三家确属酒店、排序和日期正确、三条路线均从对应酒店步行到同一终点、选店为最短、回复地点/价格/分钟数与原文一致。真实订单已经存在时，用测试订单或停在确认页对照；停在确认页只记为“选择正确”，不能作为“已预订”的成功样本。用量从任务开始量到结束，另行注明任务后学习开销。分别给出已核实成功数 / 尝试数、成功与失败合计费用、缓存占比、额外回读和每个成功任务支出。一次复测能验证该次任务，不能证明总体成功率不下降。只有在不同任务上重复 A/B、成功率无明显回退且实际费用下降后，再扩大使用范围。

发布前本机检查：核心全量 JUnit 3,123 项（5 项跳过，0 失败），再单跑包含新增同名两次纠正用例的 `ReliableMemoryTest`；Android JVM 1,862 项通过。CLI 的 82 项 Python 测试及跨语言契约、中继集成、设备测试的 Kotlin 编译均通过；未连接设备执行 instrumentation。成本脚本 3 项、翻译工具 12 项通过，11 种界面语言的资源检查通过。

## 第二轮：在同一条酒店轨迹上比较缓存费用

取一次人工验收成功、只开「精简任务历史」的 34 次请求：保留 33 次工具动作的名称和顺序、两个工具错误及末次回复位置。纯 protobuf 没有原请求正文；酒店、价格、路线、可访问性树和参数换成固定样例。每组都从相同起点算出前三家中步行时间最短者，再用算出的酒店打开模拟订单页，核对日期、酒店、地点、价格、分钟数；不填写或提交。缺一条竞争酒店的步行路线时不能宣称已找到最短者。全程未调用线上模型或真实下单接口。

下表为每次通过该回放的估算费用（元）。使用 OpenAI 兼容适配器序列化的工具和消息；工具表固定，以隔离历史处理。以相邻请求的相同前缀估算命中、用项目 TokenEstimate 估算 token，两个版本都计入参考 trace 的 8,154 输出 token。单价：命中 0.04、未命中 2、输出 8，单位为元/百万 token。不模拟服务商分块、缓存有效期、工具展开或模型因页面表达变化而增加的步骤；不含旁路费用。

| 实验 | 改写历史的请求 | 累计输入 | 其中未命中 | 估算费用 |
| --- | --- | ---: | ---: | ---: |
| 修改前（提交 `0c76c196`） | 10、11、16、22、28、34 | 1,873,934 | 361,060 | 0.847867 |
| 仅对齐时点，此后每六轮处理（对照，未采用） | 11、17、23、29 | 2,164,552 | 357,451 | 0.852418 |
| 同时处理，间隔递增 | 11、21 | 2,603,830 | 291,383 | 0.740496 |

原先的两套处理在大屏回放中分别从第 10、11 次请求开始；历史改得更短，但服务商能复用的前缀也随之变短。现在完成 10、20、40、80… 轮时一起整理较早的表格、树及重复图片，在每个时点保留最近五轮。差异基准、历史回读能力、上下文硬限和超长重试仍独立生效。较长的间隔意味着累计输入可能反而增加；若接近上下文上限、缓存优惠小或服务商不缓存，不应直接套用本组节省率。

复测入口：`./gradlew :core:test --tests '*HotelContextReplayTest'`，详见该测试的 JUnit XML 标准输出。真机比较需用前后两个构建、同一模型、同一终点，仅开「精简任务历史」；保存每次运行的用量和 trace，检查实际未命中 token、各项用量求得的整次费用及业务结果，失败尝试也计入分子。改动前已核实的三次业务成功不能作为改后的结果。
