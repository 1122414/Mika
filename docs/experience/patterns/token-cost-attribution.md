# 区分调用次数和单次输入的节省

**信号**：同一任务改动前后的总 token 差距很大，但两次走过的步骤不同。历史每多重发一次，就会多计一次输入；只比较总量，无法判断是少走了步骤，还是相同步骤的请求变短了。

**已知案例**：[上游 #223 的维护者对照](https://github.com/wangzan101/Mika/issues/223#issuecomment-6648888005) 分开报告了两组结果：同模型错误路由的只读样本从 20 步变为 7 步，输入约从 86.5 万降至 20.1 万；逐步对齐时，App 列表去重约少 3,000 输入 token。当前 [TaskRun](../../../app/src/main/java/com/wangzan101/mika/task/TaskRun.kt) 已跳过主、轻角色解析为同配置时的逐步路由。不要把整次运行的差值记为裁剪收益。该样本不是当前版本的复测或普遍节省率。

**怎么核对**：对齐相同动作和工具结果，测发送视图本身省下多少；再独立从同一起点跑到任务终点，计入成功、失败、额外步骤与回读。[RunMetrics](../../../core/src/main/kotlin/com/wangzan101/mika/core/record/RunMetrics.kt) 区分主循环回复、全部逻辑调用和 HTTP 尝试；缺 usage 的尝试单列。比较费用时还要区分缓存与未缓存输入。[RunTrace](../../../core/src/main/kotlin/com/wangzan101/mika/core/trace/RunTrace.kt) 能定位首个变动块，但仅凭前缀变动不能推出服务商实际收了多少钱。

**用量导出验证（一次）**：按 [RunStore 的导出字段](../../../app/src/main/java/com/wangzan101/mika/record/RunStore.kt) 和 [ModelCalls 的统计范围](../../../core/src/main/kotlin/com/wangzan101/mika/core/record/RunEvent.kt) 核对一份完整样本：逐步合计与运行汇总有差额，两者不能相加。用 `model_calls` 计运行总量，用 `model_reply` 定位相邻请求的输入增幅；工具名是该次回复提出的调用，导出不含工具结果正文，不能据此断定增量来自哪一块。运行结束后的记忆提取等调用不在该汇总内。

**实机对照（一次，终点不同）**：一侧只有用量导出、另一侧只有 trace 时，用 `model_reply` 对齐带 usage 的主循环 `chat` 请求，另查重试或漏报。一次对照中，主循环总输入少了 28.3%，未缓存输入却多了 93.6%；8 次首个变化位于已有消息的请求占新版未缓存输入的 50.4%。这个比例能指引回放排查，不等于这 8 次变化导致的额外消耗。全程费用仍需要同次全调用用量和适用单价。

**复测与计价**：第二份独立 trace 在第 10、11、16、22、28、34 轮也出现历史消息前缀变化，这 6 轮占该次未缓存输入的 55.2%；另一份仅含用量的记录在相同 6 轮占 47.1%，但不能据此断言其前缀也发生了变化。用[成本对照脚本](../../../eval/usage_compare.py)核对两份完整用量：在未命中单价为命中 50 倍的给定价表下，输入少 50.7% 的一次运行反而贵 13.2%。回放应同时比较未缓存输入、总成本和证据可读性。若总输入与输出固定，达到基线还需转为命中的 token 数等于「费用差 × 一百万 ÷（未命中单价 − 命中单价）」，仅用于设定实验目标。单价按每百万 token 计，脚本的参数顺序为未命中、命中、输出。

**成功标签的边界**：若验收约定是停在指定页面，分别记录用户核实的页面及回复、运行器报告的 outcome、trace 自身的完整性。本次前者通过，运行以 `end_not_done` 收尾；另有 `partial: nesting_limit`，表示本地采集视图达到嵌套上限。三者可以同时成立。[导出实现](../../../core/src/main/kotlin/com/wangzan101/mika/core/trace/TraceFiles.kt) 的纯 protobuf 不含请求或回复正文，不能凭工具名还原页面、追问理由或逐条验证候选。比较成功率时给 A/B 写入相同终点，仍须做多次独立验证。

**同轨定位与反例**：用 [34 次请求回放](../../../core/src/test/kotlin/com/wangzan101/mika/core/agent/HotelContextReplayTest.kt) 的同一序列分别运行表格整理和大树归档。改动前基线 `0c76c196`：前者在第 10 步第一次改变过去的消息；后者还要求至少 10 个已完成往返，所以大屏样本在第 11 步才第一次归档；两者随后均在 16、22、28、34 步改写。固定工具表时也会发生，与线上第 3、7 步工具列表变化可以区分。按项目的 [OpenAI 兼容请求回放计量](../../../core/src/test/kotlin/com/wangzan101/mika/core/agent/HotelReplayMeter.kt)，单纯对齐后继续每六轮处理，尽管改写从六次变四次，费用反从 0.8479 升到 0.8524。改用共同的递增间隔后为 0.7405：判断依据是重新发送的未命中 **token 数**，而非改写的 **次数**。以上仅在固定工具序列、合成页面、相邻请求公共前缀缓存模型上验证；不推断原真机逐字段原因或改后实际账单。

**整项改造的验收基线**：按用户指定的改造前原始版本计每次成功任务的整次费用；与前一实验版本的差额只能解释单项修订。酒店案例中，原版整次 1.5167416 元，当前版本整次 1.4840174 元，差 0.0327242 元（2.16%）；未缓存输入从 529,218 增至 612,944。原版完成预订、当前版停在订单页，该对照各仅一例，未证实费用稳定优于基线。用户指定了 10:41 的原始用量导出，所有新版的降费百分比固定对这次的 1.5167416 元计算，失败尝试的支出也计入。重编的旧 APK 无法证明与原包一致；若为隔离终点差异再跑，其费用单列，不能改写分母。

**改后真机核对（第一例，33 步）**：在 `fa5d937f` 的一次已核实成功、仅启用精简历史的 33 次主循环请求中，首个变化落在已有消息的只有第 11、21 步，与回放预测一致。与改前最相近的 34 步成功样本相比，运行期全部输入多 12.5%，未缓存输入少 22.8%，按相同单价算整次费用少 18.1%。两条轨迹不完全相同，这不是固定轨迹的服务商 A/B 或成功率结论。另一个可区分的机制是第 7 步：核对相邻请求的同一工具定义位置，前一请求为 `schedule_task`，后一请求为 `history_read`；对应 [AgentLoop 的工具提供时机](../../../core/src/main/kotlin/com/wangzan101/mika/core/agent/AgentLoop.kt)。工具列表改变与历史消息改写应分开计数，不能把该步全部未命中都归为可节省成本。

**第二例（44 步，跨过 40 轮）**：在同一构建、同一配置及相同人工验收终点下，前 33 次请求的费用反而低于第一例；多出的 11 次含新的整理点。第 41 次请求前后，同一工具消息从带 `tree/elements` 变为带 `archiveKey/elementTables`，当次报告 184,204 个未命中输入 token。这说明账应拆成「操作路径长度」和「是否跨过整理点」两部分；单步所有未命中并非可节省量。后续应在同一长轨迹上对照整理与暂缓，并核对后续请求、证据可读性及窗口余量。两次成功的整次费用均值 1.7738 元，高于原始基线单例 1.5167 元；单看较短样本会误判。

**区分旧屏幕改写和尾部事实移动（适配器已验证，真机配对待测）**：改为正常窗口只追加后，两条合成轨迹在 34 和 45 次请求都不再改写旧屏幕；另用 [RequestPrefixTest](../../../core/src/test/kotlin/com/wangzan101/mika/core/agent/RequestPrefixTest.kt) 单独固定一个有来源的事实，即使任务未压缩、旧屏幕没变，新增历史也会占据上一请求末尾事实块的位置，出现真实的 history 事件。不要删除事件让指标“归零”，也不要把全部后缀都归给事实。先查看同模型的步骤、首个变化位置、事实块估计长度，再对照服务商命中与整次费用。普通用量导出的估算后缀并非服务商未命中；详见[本轮方案与实测入口](../../dev/2026-11-12_缓存优先降费实施方案.md)。

**真机反例：前缀稳定和高命中率不保证单次省钱。** [新版 B 组首两次实测](../../dev/2026-11-12_酒店任务新版首批真机费用.md)逐步核对两份 trace、主循环与整次用量。两次都只有展开手机工具组打断前缀，没有旧消息改写；49 步样本命中率 95.72% 仍比原始基线贵 15.53%，33 步样本命中率较低（93.87%）反而省 24.47%。应同时看未命中**绝对数**、命中输入的累计费用和操作路径，特别是按跨应用切换定位额外请求。两例事实投影均为空；不能用来否定上面的非空尾块反例。

**首次元素表格的真机对照**：[完整七次对账](../../dev/2026-11-12_酒店任务T5真机验收.md)中，B/C 合计命中率均约 94.8%，但每个主循环请求的平均未命中为 12,273/10,908。成本按原版整次费用验收，开关的增量另外按 B/C 比；按步数、去掉最快样本的敏感性检查可检验结果是否依赖单例，但不应从正式分子删除任何尝试。四次开启均达业务终点且低于原版，不能据此推广到所有任务或保证每次低于组均目标。

**提取上游补丁时重新核对归因（两条固定轨迹）**：用 `git log -S 'step >= 7'` 和上游 `807d687b` 的 `AgentLoop.refreshOffer` 核实：`history_read` 的轮次门槛由实验提交 `d86fba93` 引入、`627017d0` 撤回；上游原本没有这个门槛。实验内的修复不能算对上游的降费功能。只移植首次元素表格后，先确认上游未修改的生产源码与新开关关闭时的结果一致，再同轨开开关。34/45 步估算费用分别从 0.663574/0.937352 降至 0.594930/0.835687 元，三条路线和选店结果一致。真机组合结果不替代该独立构建的实测。移植表示法时还要检索使用方：上游 `visibleReads`、`ContextCompressor`、`HistoryPruner` 都识别原来的元素键；应覆盖快照可见、差异屏基准和压力裁剪，而不只测新格式更短。
